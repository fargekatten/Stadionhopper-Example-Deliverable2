# 6. Eksempel på GitHub issue-plan

Dette dokumentet viser hvordan en realistisk GitHub-arbeidsflyt kan se ut for oppgaven. Det er ikke en ferdig oppgave, men et eksempel på hvordan en gruppe kan dele opp arbeidet i tydelige issues.

## Must-haves

1. `Domenemodell: definere hovedentiteter`
   - Beskrivelse: Definér bruker, kamp, stadion, klubb og innsjekking.
   - Resultat: UML eller tilsvarende modell i Markdown eller diagram.

2. `Arkitektur: overordnet systemdesign`
   - Beskrivelse: Beskriv frontend, backend, database og dataflyt.
   - Resultat: diagram og tekst med begrunnelse.

3. `UX: wireframes for hovedbrukerflyter`
   - Beskrivelse: Lag wireframes for innlogging, profil, innsjekking, feed og arrangement.
   - Resultat: tekst/diagram med begrunnelse.

4. `Git-strategi: utviklingsmodell`
   - Beskrivelse: Definér branching, PR, review, merge og samarbeidsflyt.
   - Resultat: dokumentert strategi i repoet.

5. `Teststrategi: bakover og fremover`
   - Beskrivelse: Beskriv enhet-, integrasjon- og akseptansetester.
   - Resultat: kort strategidokument.

## Should-haves

6. `Kvalitetssikring: CI/CD-plan`
   - Beskrivelse: Lag plan for automatiske bygg og tester.

7. `Oppdater innledningen og problemstilling`
   - Beskrivelse: Sikre at konseptet og problemstilling er tydelig skrevet.

8. `Refleksjon over valg og alternativer`
   - Beskrivelse: Dokumenter hvorfor valgene ble tatt, og hva som ble vurdert bort.

## Could-haves

9. `Forbedre visualisering av diagrammer`
   - Beskrivelse: Sørg for at diagrammer er tydelige i repoet.

10. `Legg inn en kort intro til fremdriftsplanen`
   - Beskrivelse: Kort tekst som forklarer hvordan oppgaven henger sammen.

## Won't have in this version

11. `Kompleks sosial feed med direkte meldinger`
   - Beskrivelse: Ikke nødvendigvis i første versjon; dette er fremtidig utvidelse.

12. `Sanntidsdata-integrasjon med ekstern fotballkilde`
   - Beskrivelse: Teknisk interessant, men ikke nødvendig for første løsningsutforming.

## Hvordan dette brukes i praksis

Issue-listen er et godt eksempel på hvordan arbeid kan deles opp uten å miste helhetsperspektivet. Hver issue er liten nok til å løses av ett medlem, men stor nok til å bidra til den samlede deliverable-en. Det er viktig at teamet bruker GitHub for dette fordi det gir et tydelig teknisk spor av hva som er gjort og når.
